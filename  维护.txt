# HPM 项目维护文档

## 一、项目概述

**HPM（Hardware Package Manager）** 是一个嵌入式开发的声明式工具链。用户只描述「用什么芯片、接了什么设备、用了哪些引脚」，工具自动拉取驱动、解析依赖、生成代码、编译烧录。

**核心理念**：驱动是模板，硬件是参数，工具是渲染器。

**仓库结构**：monorepo，三个工具共享 `core/` 库：
- `hpm`：应用开发者用（编译固件）
- `hpm-dev`：驱动作者用（开发驱动包）
- `hpm-gui`：图形化生成 `project.json`

## 三、core 模块详解

### 3.1 `core/include/hpm/` — 公共头

| 文件 | 作用 |
|------|------|
| `hpm.h` | 总入口，版本号 |
| `types.h` | 类型别名（`DeviceName`、`PinName` 等） |
| `result.h` | `Result<T>` / `Error` / `ErrorCode` |

### 3.2 `core/src/json/` — JSON 读写

| 文件 | 作用 |
|------|------|
| `json_value.h/.cpp` | 值语义 JSON 封装，不抛异常 |
| `json_io.h/.cpp` | 解析、序列化、原子写文件 |
| `json_impl.h` | 内部头，暴露 `Impl::data` 给 json_*.cpp |

**设计**：外部头只前向声明 `Impl`，内部头（`json_impl.h`）定义它。避免 nlohmann/json 污染公共头。

### 3.3 `core/src/model/` — 数据模型

纯数据结构，无 IO、无检查逻辑。

| 文件 | 作用 |
|------|------|
| `version.h/.cpp` | semver：解析、比较、预发布排序 |
| `version_range.h/.cpp` | 版本约束：`^`、`~`、`>=`、范围 |
| `pin_capability.h` | 引脚能力：类型 + 实例 + 通道 |
| `pin.h` | 引脚：名字 + 能力列表 + shareable |
| `requirement.h` | 驱动的一条需求 |
| `provided_method.h` | 驱动提供的方法 |
| `driver_manifest.h` | 驱动清单（requirements + provides） |
| `device.h` | 用户设备实例 |
| `intermediate_device.h` | 中间虚拟设备（`__spi_a3f2`） |
| `project.h` | 项目（mcu + devices） |
| `driver_state.h` | driver.json 内存表示 + 查找方法 |
| `toolchain_spec.h` | 工具链描述 |
| `flash_config.h` | 烧录配置 |
| `chip.h` | 芯片模型：引脚表 + 工具链 + 烧录 |

**注意**：`requires` 是 C++20 关键字，`DriverManifest` 里成员名用 `requirements`。

### 3.4 `core/src/manifest/` — 清单解析

JSON → model 对象。

| 文件 | 作用 |
|------|------|
| `field_reader.h/.cpp` | 字段读取辅助，统一错误消息 |
| `project_loader.h/.cpp` | 读 project.json |
| `driver_loader.h/.cpp` | 读驱动清单 |
| `state_loader.h/.cpp` | driver.json ↔ DriverState（双向） |
| `chip_loader.h/.cpp` | 读芯片清单 |

**设计**：`FieldReader` 集中处理「缺字段」「类型错误」，错误消息带路径（`devices.door_reader.driver`）。

### 3.5 `core/src/capability/` — 能力检查

**这是 HPM 的核心价值之一**。

| 文件 | 作用 |
|------|------|
| `check_report.h` | 检查报告：错误 + 警告列表 |
| `driver_library.h` | 驱动清单集合，按名字索引 |
| `pin_allocator.h/.cpp` | 引脚分配表，冲突检测 |
| `pin_matcher.h/.cpp` | 引脚能力匹配 |
| `method_resolver.h/.cpp` | 方法能力匹配（可选，已被 checker 内联） |
| `capability_checker.h/.cpp` | 总调度 |

**输入**：`DriverState`（已展开）+ `DriverLibrary` + `Chip`
**输出**：`CheckReport`

**检查顺序**：
1. 名字唯一性（user + intermediate 全局）
2. 每个用户设备的 requires：
   - 值是另一个用户设备 → 检查方法能力
   - 值是中间设备 → 检查方法能力
   - 否则当引脚 → 检查能力 + 登记占用
3. 每个中间设备的 requires：同样检查

**分享规则**：`PinAllocator` 检查引脚 `shareable` 属性。可共享（总线信号）允许多设备用；不可共享（CS/RST）冲突报错。

### 3.6 `core/src/resolver/` — 依赖解析

把 `Project` 展开成 `DriverState`。**两阶段**。

| 文件 | 作用 |
|------|------|
| `id_generator.h/.cpp` | 生成 `__spi_a3f2` 形式随机 ID |
| `resolved_node.h` | 阶段 1 的树节点 |
| `resolver.h/.cpp` | 两阶段解析 |

**阶段 1**：递归展开成 `ResolvedNode` 树
- 从用户设备的 bindings 里按 key 取值
- 遇到 `req.type` 是驱动名 → 创建子节点（中间设备）
- `consumed` 集合防止同名 key 冲突
- `visited` 检测循环依赖

**阶段 2**：把树转成 `DriverState`
- 根节点 → `user_devices`
- 子节点 → `intermediate_devices`
- 中间设备复用：按 `(driver, pins)` 查 `created_`（本次解析）+ `existing_`（driver.json）

**版本锁定**：`lockVersion` 优先用 `existing_` 里的版本。

### 3.7 `core/src/generator/` — 代码生成

把 `DriverState` 渲染成 `driver/` 目录。

| 文件 | 作用 |
|------|------|
| `generation_plan.h` | 待写文件的列表（相对路径 + 内容） |
| `template_engine.h/.cpp` | `{{var}}` 替换（暂未用） |
| `generator.h/.cpp` | 生成 driver.h/driver.c/宏/Makefile + 复制源码 |

**生成结构**：
```
driver/
├── driver.h              用户 API
├── driver.c              胶水（hpm_init_all）
├── Makefile
├── <instance>/           每个实例一个目录
│   ├── hpm_dev.h         实例宏（DEVICE_NAME + 引脚宏）
│   ├── <driver>.c        驱动源码拷贝
│   └── <driver>.h
└── <chip>/               芯片驱动（全局一份）
    ├── <chip>.c
    └── hpm_pin.c
```

**宏值计算** `macroValue`：
- 值是某个实例名 → 直接用
- 否则是引脚名 → 加 `hpm_pin_` 前缀

### 3.8 `core/src/util/` — 工具

| 文件 | 作用 |
|------|------|
| `fs_utils.h/.cpp` | 原子写文件、读文件 |
| `process.h/.cpp` | 子进程调用（make、烧录器） |

### 4.1 `cli/src/`

| 文件 | 作用 |
|------|------|
| `main.cpp` | 入口，CLI11 解析，全局选项 |
| `cmd_context.h/.cpp` | 上下文（项目路径、缓存路径、verbose） |
| `command.h` | 命令基类 |
| `command_registry.h/.cpp` | 注册 + 分发 |
| `output.h/.cpp` | 带颜色输出 |

### 4.2 `cli/src/commands/`

| 文件 | 命令 | 作用 |
|------|------|------|
| `init_cmd.h/.cpp` | `hpm init` | 生成 project.json 模板 + .gitignore |
| `sync_cmd.h/.cpp` | `hpm sync` | 读清单 → resolve → check → 生成 driver/ |
| `build_cmd.h/.cpp` | `hpm build` | 调 make |
| `flash_cmd.h/.cpp` | `hpm flash` | 读芯片驱动 flash 配置，调烧录器 |
| `clean_cmd.h/.cpp` | `hpm clean` | 删 build/ |
| `dev_export_cmd.h/.cpp` | `hpm dev --export` | 生成 hpm.h（底层逃生舱） |

### 4.3 `hpm sync` 流程

```
1. 读 project.json → Project
2. 读已有 driver.json → DriverState（可空）
3. 从本地包目录加载芯片驱动 → Chip
4. 从本地包目录加载所有驱动 → DriverLibrary
5. Resolver.resolve() → DriverState
6. CapabilityChecker.check(state) → 报错就停
7. 写 driver.json
8. Generator.generate() → driver/
```

## 五、关键设计约定

### 5.1 宏体系

**两套宏，作用不同。**

**`hpm_dev.h`**（每个实例一份，工具生成）：
```c
#pragma once
#define DEVICE_NAME  door_reader
#define bus  __spi_a3f2
#define cs   hpm_pin_PA4
#define rst  hpm_pin_PA3
```

**驱动源码自带拼接宏**（每个驱动重复写）：
```c
#define HPM_CAT_(a, b) a##b
#define HPM_CAT(a, b)  HPM_CAT_(a, b)
#define HPM_FN(name)   HPM_CAT(DEVICE_NAME, HPM_CAT(_, name))
#define HPM_CALL(prefix, method)  HPM_CAT(prefix, HPM_CAT(_, method))
#define HPM_STR_(x)    #x
#define HPM_STR(x)     HPM_STR_(x)
```

**关键点**：**C 预处理器只匹配独立 token**。`cs` 宏不会匹配 `cs_init` 里的 `cs`。必须用拼接宏 `HPM_CALL(cs, init)`。

### 5.2 多实例编译

同一驱动多个实例时，**每个实例一个目录，编译两次**：
```
driver/door_reader/rc522.c   编译时 -Idoor_reader → DEVICE_NAME=door_reader
driver/gate_reader/rc522.c   编译时 -Igate_reader → DEVICE_NAME=gate_reader
```

驱动源码**只写一份**，靠 `-I` 切换 `hpm_dev.h`。

### 5.3 引脚的函数前缀

`cs` 宏的值是 `hpm_pin_PA4`，`HPM_CALL(cs, init)` → `hpm_pin_PA4_init`。芯片驱动必须提供 `hpm_pin_<PIN>_<method>` 形式的函数。

工具只负责生成 `#define cs hpm_pin_PA4`，芯片驱动的实现是它自己的事。

### 5.4 driver.json 结构

```json
{
  "user_devices": {
    "door_reader": {
      "driver": "rc522",
      "version": "1.2.0",
      "bus": "__spi_a3f2",
      "cs": "PA4",
      "rst": "PA3"
    }
  },
  "intermediate_devices": {
    "__spi_a3f2": {
      "name": "__spi_a3f2",
      "driver": "spi",
      "version": "1.0.0",
      "sck": "PA5",
      "miso": "PA6",
      "mosi": "PA7"
    }
  }
}
```

- 用户可改 `name`（引用它的 `bus` 字段自动跟改）
- 版本锁定后沿用
- **提交 git**（和 project.json 一起）

## 七、如何写一个新的驱动包

### 7.1 目录结构

```
mydevice-1.0.0/
├── manifest.json
├── src/
│   └── mydevice.c
└── include/
    └── mydevice.h
```

### 7.2 `manifest.json`

```json
{
  "name": "mydevice",
  "version": "1.0.0",
  "description": "My device driver",
  "requires": {
    "bus": { "type": "spi", "methods": ["transfer"] },
    "cs":  { "type": "gpio_out", "methods": ["write"] },
    "rst": { "type": "gpio_out", "methods": ["write"], "optional": true }
  },
  "provides": {
    "methods": ["init", "read_card"]
  }
}
```

**requires 的 key** 会成为 `hpm_dev.h` 里的宏名。
**requires 的 type**：
- 是驱动名（如 `"spi"`）→ 工具递归创建中间设备
- 否则是引脚能力（如 `"gpio_out"`）→ 工具从上层 bindings 里取对应引脚

### 7.3 `include/mydevice.h`

```c
#pragma once
#include "hpm_dev.h"
```

**注意**：`hpm_dev.h` 由工具生成，驱动包里**没有这个文件**。编译时 `-I<instance>` 让编译器找到它。

### 7.4 `src/mydevice.c`

```c
#include "mydevice.h"
#include <stdio.h>

// 拼接辅助宏（每个驱动都自带）
#define HPM_CAT_(a, b) a##b
#define HPM_CAT(a, b)  HPM_CAT_(a, b)
#define HPM_FN(name)   HPM_CAT(DEVICE_NAME, HPM_CAT(_, name))
#define HPM_CALL(prefix, method)  HPM_CAT(prefix, HPM_CAT(_, method))
#define HPM_STR_(x)    #x
#define HPM_STR(x)     HPM_STR_(x)

// 实现 provides 声明的方法
// 函数名必须用 HPM_FN 拼接，实例化后是 <DEVICE_NAME>_<method>
int HPM_FN(init)(void) {
    printf("[mydevice:%s] init\n", HPM_STR(DEVICE_NAME));

    // 用引脚
    HPM_CALL(cs, init)();
    HPM_CALL(cs, write)(1);

    // 用总线
    HPM_CALL(bus, init)();

    return 0;
}

int HPM_FN(read_card)(void) {
    printf("[mydevice:%s] read_card\n", HPM_STR(DEVICE_NAME));

    unsigned char tx[4] = {0x01, 0x02, 0x03, 0x04};
    unsigned char rx[4] = {0};
    HPM_CALL(bus, transfer)(tx, rx, sizeof(tx));

    return 0;
}
```

### 7.5 放到包目录

```bash
mkdir -p ~/.hpm/packages/mydevice-1.0.0/{src,include}
# 把上面文件放进去
```

### 7.6 在项目里用

`project.json`：
```json
{
  "mcu": "stm32f103c8t6",
  "devices": {
    "my_dev": {
      "driver": "mydevice",
      "cs": "PA4",
      "sck": "PA5",
      "miso": "PA6",
      "mosi": "PA7"
    }
  }
}
```

`hpm sync` 会：
- 识别 `mydevice` 驱动
- 递归展开 `bus` → 创建中间设备 `__spi_xxx`
- 从 `my_dev` 里取 `sck`/`miso`/`mosi` 给 spi
- 生成 `driver/my_dev/hpm_dev.h`：
  ```c
  #define DEVICE_NAME  my_dev
  #define bus  __spi_xxx
  #define cs   hpm_pin_PA4
  ```
- 生成 `driver.h`：`int my_dev_init(void); int my_dev_read_card(void);`

## 八、如何写芯片驱动包

### 8.1 目录结构

```
stm32f103c8t6-1.0.0/
├── chip.json
├── src/
│   ├── stm32f103c8t6.c
│   └── hpm_pin.c           每个引脚的函数
└── include/
    ├── stm32f103c8t6.h
    └── hpm_pin.h
```

### 8.2 `chip.json`

```json
{
  "name": "stm32f103c8t6",
  "family": "stm32f1",
  "package": "LQFP48",
  "toolchain": { "name": "arm-none-eabi-gcc" },
  "flash": {
    "tool": "st-flash",
    "args": ["write", "{bin}", "0x8000000"]
  },
  "pins": {
    "PA4": { "capabilities": [{ "type": "gpio_out" }] },
    "PA5": { "shareable": true, "capabilities": [{ "type": "spi_sck", "instance": "SPI1" }] },
    "PA6": { "shareable": true, "capabilities": [{ "type": "spi_miso", "instance": "SPI1" }] },
    "PA7": { "shareable": true, "capabilities": [{ "type": "spi_mosi", "instance": "SPI1" }] }
  }
}
```

**capabilities 的类型**：
- `gpio_out` / `gpio_in`：普通 GPIO
- `spi_sck` / `spi_miso` / `spi_mosi`：SPI 信号
- `i2c_scl` / `i2c_sda`：I2C
- `uart_tx` / `uart_rx`：UART
- 未来扩展：`tim_ch`、`adc` 等

**shareable**：总线信号（SCK/MISO/MOSI/SCL/SDA）应设为 true。

### 8.3 `src/hpm_pin.c`

为每个引脚提供 `<prefix>_init`、`<prefix>_write`、`<prefix>_read`：

```c
#include "hpm_pin.h"
#include <stdio.h>

#define DEF_PIN(name) \
    void hpm_pin_##name##_init(void)       { printf("[pin] " #name " init\n"); } \
    void hpm_pin_##name##_write(int level) { printf("[pin] " #name " write %d\n", level); } \
    int  hpm_pin_##name##_read(void)       { return 0; }

DEF_PIN(PA3)
DEF_PIN(PA4)
DEF_PIN(PA5)
DEF_PIN(PA6)
DEF_PIN(PA7)
```

**函数命名约定**：`hpm_pin_<PIN>_<method>`。工具生成的 `hpm_dev.h` 里 `#define cs hpm_pin_PA4`，驱动源码 `HPM_CALL(cs, init)` 展开成 `hpm_pin_PA4_init`。

### 8.4 烧录配置

`flash.tool` 是烧录器命令，`flash.args` 支持占位符：
- `{bin}` → `build/firmware.bin`
- `{elf}` → `build/firmware.elf`
- `{hex}` → `build/firmware.hex`

例：`st-flash write {bin} 0x8000000`

## 九、还没做的事

### 9.1 高优先级

| 项 | 说明 |
|----|------|
| **registry 客户端** | 从 GitHub 拉驱动包和索引，解压到 `~/.hpm/cache/packages/` |
| **toolchain 管理** | 从芯片驱动读工具链，检查全局缓存，没有就下载 |
| **hpm-dev** | 驱动包的 init/test/validate/publish |
| **方法签名解析** | `driver.h` 生成的函数签名从 `provides.methods[].signature` 解析 |
| **Makefile 从芯片驱动读工具链** | 现在硬编码 `PREFIX ?=`，应从 `chip.toolchain.name` 提取前缀 |
| **Makefile 源文件扫描** | 现在假定 `<instance>/<driver>.c`，应扫描目录 |
| **芯片驱动的引脚自动生成** | 从 `chip.json` 的 pins 列表生成 `hpm_pin.c` |

### 9.2 中优先级

| 项 | 说明 |
|----|------|
| **增量生成** | 内容哈希对比，跳过未变的文件 |
| **日志系统** | 分级、颜色、文件输出 |
| **中间设备改名流程** | 用户改 `driver.json` 里的 name，引用自动跟改 |
| **`hpm.h` 完整实现** | 现在只生成最小版，应暴露引脚操作 + 中间接口 |
| **集成测试** | 完整 sync + build 流程 |
| **多实例驱动的源码扫描** | 支持一个驱动多个 `.c` 文件 |
| **链接脚本和启动文件生成** | 从芯片驱动读 |

### 9.3 低优先级

| 项 | 说明 |
|----|------|
| **hpm-gui** | Qt 图形化生成 project.json |
| **KiCad 导入** | 从 `.kicad_sch` 生成 project.json |
| **AI 驱动包生成** | 从文档 + 开源代码整理驱动包 |
| **多镜像支持** | 项目/用户/全局优先级 |
| **许可证处理** | 驱动包带 license 信息 |
| **签名校验** | 包完整性 |
| **离线完整支持** | 索引缓存、按需拉包 |
| **CI 配置** | GitHub Actions |
| **文档站点** | docs/ |

### 9.4 已知简化

| 简化 | 影响 |
|------|------|
| `ProvidedMethod.signature` 不解析 | `driver.h` 签名硬编码 `int fn(void)` |
| `PinMatcher` 不校验 instance | SPI1 vs SPI2 不区分 |
| `VersionRange` 不支持 `\|\|` | 复杂约束写不了 |
| `hpm_dev.h` 无声明 | 驱动源码编译靠隐式声明或手动 extern |
| 中间设备 ID 随机 | 每次 sync 复用已有的，但首次随机 |
| Makefile 只支持一种编译选项 | 优化等级、宏定义不可配 |
| 只支持一个总线 | 一个设备同时用多个总线会冲突 |

## 十、开发流程

### 10.1 编译

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build -j
```

### 10.2 测试

```bash
ctest --test-dir build --output-on-failure
```

### 10.3 跑 CLI

```bash
./build/bin/hpm --version
./build/bin/hpm init --mcu stm32f103c8t6
./build/bin/hpm sync
./build/bin/hpm build
```

参考 `make-mock-packages.sh`（在 `/tmp/hpm-test/` 或项目根），生成 `~/.hpm/packages/` 下的测试包。

### 10.5 排查问题

**编译错误**：检查 `hpm_dev.h` 是否被正确生成，`-I` 路径是否正确。

**链接错误**：
- `undefined reference to cs_init`：`cs` 宏未展开，驱动源码用了 `cs_init()` 而不是 `HPM_CALL(cs, init)`
- `undefined reference to hpm_pin_PA4_init`：芯片驱动未提供该引脚函数

**能力检查失败**：看错误消息的 `location`（`devices.door_reader.cs`），检查 project.json 里的引脚是否冲突或能力不匹配。

## 十一、给未来的自己

1. **能力检查是 HPM 的核心价值**，改动要谨慎，测试要全。
2. **宏体系是最容易出错的地方**。C 预处理器的 token 规则必须牢记：`cs` 不匹配 `cs_init` 里的 `cs`。
3. **两阶段 resolver**（展开 + 摊平）比一阶段清晰得多，别图省事合并。
4. **driver.json 提交 git**，driver/ 不提交。前者锁定状态，后者是产物。
5. **每个实例一个目录**是最简方案，多实例编译两次。后续优化可以改成「模板 + 运行时分发」，但先跑通再说。
6. **芯片驱动是唯一碰寄存器的层**。上层驱动只用 `hpm_pin_*` 和 `HPM_CALL(<prefix>, <method>)`。
7. **`hpm_dev.h` 极简**，只有 `DEVICE_NAME` + 资源宏。拼接宏由驱动源码自带。
